# Offline subscription licensing

## Trust and wire format

The vendor signs with Ed25519 on an operator-controlled workstation. The
customer's Django server verifies using a local, operator-installed public-key
manifest. The Angular browser receives status and verified display metadata.
Payment, delivery, key installation, activation, and renewal require no online
license service.

Version 1 is SMS1 followed by two dot-separated unpadded base64url values.
They contain the UTF-8 JSON payload and its Ed25519 signature. JSON uses sorted
keys, compact separators, no escaping of non-ASCII text, and exact byte
round-tripping. The signed fields are version, license_id, institution_id,
institution_name, installation_id, edition, issued_at, valid_from, expires_at,
duration, features, key_id, and grace_days. IDs are canonical UUIDs. Features
are sorted unique identifiers. Instants are UTC with whole seconds and a Z
suffix. Institution ID and installation ID bind the license. Institution name
is a signed display label and can differ after an authorized local rename.

Both issue time and valid-from must be reached. Expiration is exclusive. Date
arguments without a time mean midnight UTC. Monthly terms add 1, 3, 6, or 12
calendar months to the original start, keeping the time and clamping the day to
the last valid day in the destination month. For example, 31 January 2028 at
20:30 UTC plus one month expires on 29 February at 20:30 UTC. Custom terms
require an explicit exclusive end. The CLI requires --approve before signing
and reports the interval if approval is absent.

## Vendor operation

Run the following from a private vendor checkout. Place key storage outside the
checkout and customer distribution. For production omit --test-only. The
keygen command uses an interactive passphrase and writes encrypted PKCS#8.
Limit OS access to the vendor operator and use protected backups. No key is
generated by migrations, application startup, frontend builds, or packaging.

    .venv/bin/python vendor-tools/license-generator/license_tool.py keygen \
      --key-id vendor-2026 --private-key /secure/vendor/vendor-2026.pem \
      --public-keys /secure/vendor/vendor-2026-public.json

    .venv/bin/python vendor-tools/license-generator/license_tool.py issue \
      --key-id vendor-2026 --private-key /secure/vendor/vendor-2026.pem \
      --institution-id "$INSTITUTION_ID" --installation-id "$INSTALLATION_ID" \
      --institution-name "$INSTITUTION_NAME" --edition standard --duration 1m \
      --valid-from "$(date -u +%F)" --grace-days 3 --feature dashboard \
      --approve --out renewal.smslicense

    .venv/bin/python vendor-tools/license-generator/license_tool.py verify \
      --public-keys /secure/vendor/vendor-2026-public.json --license renewal.smslicense

Key manifests map signing key IDs to unpadded base64url raw Ed25519 public keys.
Install a trusted manifest from the vendor through an authenticated channel.
Set LICENSE_PUBLIC_KEYS_FILE to its absolute path. Protect the manifest from
ordinary application users and deploy changes atomically. Add the new public key
before issuing with it. Keep older public keys as long as their licenses or
verified history are needed. Removing a key disables verification of all
licenses signed by it, including archived metadata.

## Customer activation and renewal

After institution setup, open Subscription and copy both IDs. Send them to the
vendor through the agreed channel. An authorized administrator can import the
returned .smslicense file or paste its contents in Activation. Same-origin
session authentication, CSRF and role permissions apply. Both values must
match the installation. Re-importing the current token is idempotent. A
renewal must be valid at import time, use a new license ID, have an equal or
later issue time, and extend the current verified expiration. The previous
activation remains in history. Future licenses can be kept offline and imported
when their interval begins.

## Availability and clock policy

Active and expiring subscriptions allow licensed business writes after normal
authorization. Reminders appear at 15, 7, 3, and the final day or expiry.
The grace deadline uses the smaller of the signed day count and the local
LICENSE_MAX_GRACE_DAYS cap. The default grace policy is read-only.
LICENSE_GRACE_WRITES enables writes within that signed interval. Expired,
missing, invalid, or clock-review states deny ordinary business writes.
Existing reads, export and backup handlers, authentication, Phase 03
administration, renewal, and recovery keep their normal permissions. Student
and financial APIs remain future work. Enforcement is exercised against
isolated test views with the same DRF permission class.

Verification tracks a local UTC high-water mark, using the higher of the
observed time and the last verified time. A backward jump beyond
LICENSE_CLOCK_TOLERANCE (default 300 seconds) triggers review and audit.
Correct the server clock to clear review after it reaches the high-water mark.
The backend never modifies records as an expiration or clock penalty.

## Restore, transfer, and reissue

Institution identity, installation ID, activation history, and clock state are
included in the PostgreSQL backup. Hardware replacement or an exclusive server
migration retains identity when the original database is restored intact and
the previous instance is retired. A fresh database generates a new identity.
A clone of a backup shares its installation ID, so only one copy should be
operated under the transferred license. An authorized operator and vendor can
arrange a reissue for a fresh identity, including recovery from an incorrect
future high-water mark.

    .venv/bin/python backend/manage.py reissue_installation --confirm "$CURRENT_INSTALLATION_ID"

This clears the active pointer and rotates the installation ID without removing
historical activations. Request a new signed license bound to the returned ID.
Reserve this command for coordinated recovery. Offline installations cannot
detect copied databases reliably. A privileged operator can alter the clock,
application or trusted key list. Clock protection is best effort and restoring
an older database also restores its old clock checkpoint.

## Phase 09 human resources and payroll

See [Human resources](HR_MANAGEMENT.md) for employment, staff attendance, compensation, protected payroll records and local deployment.

Phase 09B uses the existing offline licensing gates. Attendance, leave
and document writes use the HR feature. Overtime policy, request and approval
writes use the payroll feature. Authorized reads and existing exports remain
available according to the installed license's read-only behavior.

Leave policy revision and posting writes require active signed HR entitlement
after RBAC. Authorized policy history and ledger reads remain available after
expiry.

Salary structure draft, submission, decision, and activation writes require
a current payroll entitlement. Authorized users retain read access to existing
structures, approval history, and payroll artifacts after license expiry.

Add `timetables` to the signed feature list for institutions entitled to
timetable writes. Published schedules and authorized exports remain readable
after expiry. Existing attendance, examinations and HR operations retain
their previous entitlement checks.

Phase 10B group, workload and cross-date writes use the signed
`timetables` entitlement. Authorized history, reports and exports remain
readable independently of timetable write eligibility.
